PyTorch and NumPy both report Apple Accelerate as their BLAS (`BLAS_INFO=accelerate`, NumPy

use, so for GEMM it is a reference well beyond what our CPU code can reach on this machine.

## Results

"Ours / reference" is the reference's time divided by ours: 1.00 is parity and above 1.00 means we are
faster. Times are medians of 9 samples.

Notes on fairness:

- `torch.nn.functional.pad` has no `out=` argument, so PyTorch allocates (and the OS zero-fills) a new
  output on every call while our benchmark writes into preallocated memory. Part of the pad gap is that
  allocation, not the copy.
- At 1,000 elements every PyTorch and NumPy call costs about 1 µs of Python and dispatch overhead; ours
  is called directly from C++ (0.16 µs). Those rows are left out of the table because they compare call
  overhead, not kernels.
- `split` itself returns views in both libraries (1 µs for us, 7 µs for PyTorch). The packing after it is
  `Tensor::contiguous()`, which is not parallel yet (that is Vedad's task), so our row does not speed up
  with threads.

### How close to the hardware

- **Memory-bound ops** (concat, pad, ger): the large out-of-cache cases reach 124 to 150 GB/s. The
  M3 Pro's advertised memory bandwidth is 150 GB/s; the team's measured all-threads copy benchmark (Vedad's
  task) does not exist yet, so there is no measured ceiling to divide by. One thread's `memcpy` of the
  same bytes reached 91 to 132 GB/s in the same runs.
- **Batched GEMM** (compute-bound): there is no measured FMA peak for this machine, because
  `fma_peak_benchmark` is x86-only (it includes `immintrin.h` and does not build on ARM). Our best,
  222 GFLOP/s, comes from the plain fallback loops on 11 cores.

## Problems found

1. **The elementwise parallel cutoff was far too low for copies.** With `parallel_threshold` (32,768
   elements), `concat` and `pad` ran 6 to 9 times slower on 11 threads than on one just above the cutoff
   (a 64 x 1024 concat at 0.17x, a 181 x 181 pad at 0.11x): waking the threads cost more than copying
   130 KB. Both now use `parallel_work_threshold` (262,144 elements); the table above is from the run after
   the change, and the same sizes now stay on one thread (1.00x).
2. **The first PyTorch GEMM run used one thread only.** The script set `MKL_NUM_THREADS=1` to keep
   NumPy's BLAS on one thread, and PyTorch reads that variable as its own thread count
   (`at::get_num_threads() : 1`). The script now leaves the environment alone and takes the thread
   counts from `os.cpu_count()`.

## Why we are behind on batched GEMM, and what to try

- **Not vectorized for ARM.** On this machine every matrix goes through the plain i-k-j fallback, because
  the packed kernel is AVX2-only. A NEON (or SVE) micro-kernel for the packed GEMM would make the batched
  version faster with no change of its own, as it only calls the packed GEMM.
- **The reference uses different hardware.** Accelerate runs `sgemm` on the AMX unit (1,364 GFLOP/s for
  4 x 512³ on one thread). The NEON cores cannot reach that, so the fair targets on this machine are
  OpenBLAS (not installed here; Homebrew's `openblas64` exports only `cblas_sgemm64_`) and our own x86
  numbers on the team's i7 and Ryzen, where the packed AVX2 kernel runs.
- **Small matrices are already ahead.** For 1024 matrices of 8 x 8 we are 2.9x faster than `torch.bmm`,
  which pays per-matrix overhead that `over_batch` does not.

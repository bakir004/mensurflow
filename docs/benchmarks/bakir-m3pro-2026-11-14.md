**GPU clock.** The GPU only reaches its full clock after some time under load. One warm-up call is not
enough: a 2048^3 product timed straight after start-up ran at a third of its speed. The Metal sweep
therefore runs matmuls for one second before the first row.

## What I ran

```
build/matmul_tile_benchmark
```

Metal goes through `mensurflow::matmul(a, b, Execution::GPU)`, so every call allocates its output,
encodes one command buffer and waits for it. MPS (`MPSMatrixMultiplication`) is called the same way
through kernel 2. The CPU rows call `matmul_f32_parallel` directly on 11 threads. Every configuration
is checked against the first one before it is timed. The inputs are multiples of 0.25 in [-4, 4], so
every product and sum is exact and all configurations must give the same values.

## Results: Metal (GFLOP/s, second run)

| shape (m x n x k) | MPS | default: simd 32x64x16, 2x2 simdgroups | vs MPS | best other simd | tiled 64x64x16, 4x4 per thread |
|---|---:|---:|---:|---:|---:|
| 256^3 | 179 | 248 | 1.38x | about the same | 186 (first run) |
| 512^3 | 1041 | 1133 | 1.09x | 64x64x16 4x2: about the same | 787 (first run) |
| 1024^3 | 2582 | 2287 | 0.89x | 64x32x16 2x2: 2225 | 1264 |
| 2048^3 | 3578 | 2925 | 0.82x | 64x64x32 2x4: 2830 (first run) | 1503 (first run) |
| 4096^3 | 3881 | 2956 | 0.76x | 64x64x32 2x4: 2834 | 1546 |
| 4096 x 1024 x 1024 | 3021 | 2566 | 0.85x | | |
| 1000^3 | 2214 | 1890 | 0.85x | | |
| 64 x 4096 x 4096 | 2313 | 1860 | 0.80x | 64x64x16 4x2: 1984 (first run) | |

- **Accumulators per simdgroup decide the speed.** A simdgroup that owns 2 x 2 or 2 x 4 blocks of
  8 x 8 runs at full speed. One that owns 4 x 4 blocks runs at a third of it (64x64x16 with 2 x 2
  simdgroups: 875 GFLOP/s at 4096^3), at every size. Every slow configuration I measured had 16
  accumulators of 8 x 8 per simdgroup; the likely cause is register pressure.
- **Loads.** Loading the staged slices four floats at a time (`packed_float4`) raised 32x32x16 from
  2000 to 2600 GFLOP/s at 2048^3. Padding the staged rows against bank conflicts and `#pragma unroll`
  changed nothing measurable, so neither is in the kernel.
- **Small products are faster than MPS** (1.1x to 1.4x at 256^3 and 512^3). MPS creates its kernel
  object on every call, and our pipeline is cached. From 1024^3 up, MPS stays 11 to 24% ahead. It
  probably double-buffers its slices so loads overlap the multiplies, which our kernel does not do yet.
- The plain tiled kernel (no `simdgroup_matrix`) tops out at about 1.5 TFLOP/s, 0.4x MPS. It is the
  fallback for GPUs older than Apple family 7.

## Results: CPU tile sizes (GFLOP/s on 11 threads, second run)

| shape | default (band x 128 x 256) | band x 512 x 1024 | 4 x 64 x 1024 | worst measured |
|---|---:|---:|---:|---:|
| 512^3 | 135 | 160 | 172 (first run) | 133 (band x 256 x 256) |
| 1024^3 | 140 | 170 | 164 | 127 (band x 128 x 128) |
| 2048^3 | 133 | 138 | 135 (first run) | 119 (16 x 256 x 512, first run) |
| 4096 x 1024 x 1024 | 143 | 172 | 168 (first run) | 135 (band x 128 x 128, first run) |

Every tile size gives the same bits, which the benchmark checks. Wider column blocks (1024) are up to
1.2x faster than the default at three of the four shapes and equal at 2048^3. I did not change the
default, because which tile size is best depends on the shape, and that choice is for the auto-tuner.
The portable loop stays far below the GPU (about 170 vs 3000 GFLOP/s).

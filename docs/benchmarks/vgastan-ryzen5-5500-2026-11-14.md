## How the comparison is made

- Same float32 inputs on both sides (the C++ and Python fill functions produce the same numbers).
- **Ours** is the CPU kernel called on preallocated buffers (normalization) or the public API, which is in
  place (optimizers). Shapes of the benchmark: BERT-sized rows (`32x768`, `1024x768`), a wide hidden size
  (`8192x1024`), 128 MB of activations (`32768x1024`), a ResNet stage (`32x64x3136` = NCHW 32x64x56x56), a
  late stage (`8x256x196`) and two `[N, C]` layouts. Optimizers: n = 1,000, 65,536, 1,048,576, 16,777,216.
- **PyTorch** uses `out=` ATen variants where they exist: `native_layer_norm.out`,
  `native_layer_norm_backward.out`, `native_batch_norm.out`, `native_batch_norm_backward.out`, and the
  fused CPU optimizer kernels `torch._fused_sgd_`, `_fused_adam_`, `_fused_adamw_` called directly. ATen has
  no `out=` for RMS norm, so `rms_norm` is `F.rms_norm` (allocates) and `rms_norm_backward` is
  `torch.autograd.grad` over it with a retained graph (allocates and goes through autograd): **those two
  ratios flatter us and should not be read as a pure kernel comparison.** PyTorch's layer-norm and
  batch-norm backward use the mean and rstd saved by the forward pass; ours recomputes them from x (the
  public API does not keep them), which is one extra read of the input.
- Every timed call is preceded by a correctness check: ours against a double-precision scalar reference
  (`tests/reference/optimizer_normalization.hpp`), and across thread counts bit for bit; PyTorch against its
  own float64 result. A 500 ms pause precedes each timed library on the Python side.
- Median of 9 samples (3 for calls over 0.2 s), each sample at least 2 ms, one warm-up call.
- "PyTorch / ours" is PyTorch's median time divided by ours: **above 1.00 we are faster**, 1.00 is parity.
  "noisy" means the spread between runs of the same side exceeds 10%.
- "% of 12-thread copy rate" is our GB/s (inputs read once, outputs written once, the byte counts in
  `optimizer_normalization_benchmark.cpp`) over the measured copy rate below.

### Measured copy bandwidth (the memory-bound ceiling)

`bandwidth_benchmark`, 64M float32 elements (256 MiB per array, larger than L3), read + write GB/s:

| threads | median ms | GB/s |
|---:|---:|---:|
| 1 | 34.34 | 15.63 |
| 12 | 19.01 | 28.24 |

The 1-thread copy rate is not a true ceiling: a streaming in-place optimizer reaches 105-113% of it (it
moves the same logical bytes without a write-allocate), so the percentages below use the 12-thread rate.
Going from 1 to 12 threads buys only 1.8x of bandwidth, which is why the large memory-bound rows scale
by 1.3x - 2.1x for the norms and not at all for the optimizers (below), instead of by 12x.

### Memory-bound ceiling

At 12 threads, the large cases (inputs of 128 MB or more) reach, as a share of the 28.24 GB/s copy rate:
SGD with momentum 92%, Adam 87%, AdamW 89%, `layer_norm` 74%, `layer_norm_backward` 92%, `rms_norm` 79%,
`rms_norm_backward` 88%, `batch_norm` (25 MB) 80%, `batch_norm_backward` 52%. At 1 thread the same cases
are 43-75% of it, except the optimizers (105-113%, which exceeds the copy rate, see above). So the large
cases of the optimizers and of the layer/RMS norms are memory bound and close to the machine, and PyTorch
is at the same place (it is within 5% of us on 12 threads for the optimizers). The shortfall of
`batch_norm_backward` (52%) is the real gap: it reads x, dy and recomputes the statistics (three passes
over x before the dx pass).

### AVX2 vs the portable loop (optimizers, same session)

`matmul`); the build stays baseline x86-64. It performs the same operations in the same order as the portable
loop, with separate multiply and add (no FMA), so **both give identical bits** (a test compares them for 10 sizes,
with and without a tail, at 4 thread counts). `optimizer_normalization_benchmark optimizers noavx2` runs the

### Tuning history (what changed because of these measurements)

The first correct implementation, measured against the same PyTorch:

- `[N, C]` batch norm (forward and backward) was **7-10x slower** than PyTorch (0.10x-0.24x). Cause:
  the row-block loop accumulated in double and the compiler could not vectorize it, and loops that stored
  to floats kept reloading the extents from the `Dims` struct (MSVC does not use type-based aliasing).
  Fix: float sums over 32-row groups added to double accumulators, extents and pointers held in locals,
  `restrict` on the streaming pointers. Forward is now 1.5x - 2.8x faster than PyTorch on `[N, C]` inputs; the
  `[N, C]` backward is 0.30x - 0.69x (open, below).
- Adam and AdamW were 0.66x - 0.94x of PyTorch's fused kernel on one thread from 65k elements up with the
  baseline SSE2 loops; the AVX2 kernels (above) fixed the cache-resident cases.
- layer and RMS norm line reductions were not vectorized by MSVC (`/Qvec-report` said so); they now use
  SSE2 intrinsics with the same eight-lane order as the portable code, so the bits are identical to the
  fallback used on other CPUs. `layer_norm` 32x768 went from 12.5 us to 7.9 us (1 thread).
- Tried and rejected: fusing the sum and the dot product of the layer-norm backward into one pass made it
  slower (1.05 ms vs 0.80 ms at 1024x768), and summing the per-block partials in cache-friendly column
  tiles made it **2x slower** (reason not found), so both were reverted.

## Stability

The machine was not quiet (Balanced power plan, Firefox, VS Code and PyCharm open), but runs A to D
agree well: for the optimizer and layer/RMS-norm code that did not change after run C, the 12-thread
median of `adam` at 1,048,576 elements was 0.116, 0.110, 0.125 and 0.109 ms in runs A to D.

**Runs E and F were contaminated and discarded.** `adam` at 1,048,576 elements on 12 threads then read 0.73 ms
and 0.50 ms with the same code, and re-measuring afterwards gave 0.40 - 0.45 ms (minimum 0.16 ms), while total
CPU load was 46% with the benchmark idle. The cause is an EVE Online client (`exefile.exe`) that the process
list showed started at 21:37:15, after run D finished (21:36:05) and before run E finished (21:43:51). I did
not notice it while the runs were going and only found it when two identical-code measurements disagreed by
5x. I did not close it because it is the user's application; it was closed afterwards on request.

What was done about it:

- Optimizers and layer/RMS norm use only runs C and D, taken before the game. Their rows are as noisy as the
  "noisy" column says (a spread over 10% between runs of the same side).
- `batch_norm` was rerun twice (G and H, three minutes apart) with the game closed and the CPU load at 5%,
  plus a third PyTorch run; those are the `batch_norm` rows. Several of them are still marked noisy
  (G and H differ by more than 10%, for example `32x64x3136` on one thread: 3.1 ms and 2.0 ms), so the
  `batch_norm` ratios near 1.0 should not be read as a win or a loss.
- The 1-thread rows and the large memory-bound rows are the most trustworthy; the 12-thread small and
  mid-size rows are the noisiest, in the PyTorch columns as well.
- The power plan stayed on Balanced throughout.

## Observations

- Large optimizer and layer/RMS-norm cases are memory bound and at 74-92% of the measured copy rate, so
  extra SIMD would not help them; PyTorch is within 5% of us there on 12 threads.
- With the portable (SSE2) loops, Adam and AdamW were 0.67x - 0.94x of PyTorch's fused kernel on one thread from
  65k elements up, where the work is arithmetic (`sqrt` and a division per element). I suspected that PyTorch's
  run-time AVX2 dispatch was the reason and added an AVX2 kernel chosen the same way: it is 1.6x - 1.7x faster at
  65k elements and brings Adam to 1.2x of PyTorch there. Where the data is larger than the cache nothing changes
  (memory bound, parity with PyTorch).
- At 1,000 elements PyTorch's fused kernel costs 2-5 us per call and `torch.optim` 45-65 us, so we are 1.4x
  to 55x faster there purely from call overhead.
- Thread scaling on the large cases is limited by the memory system (above). From 1 to 12 threads the
  32768x1024 norms speed up 1.4x (`layer_norm`), 1.3x (`rms_norm`), 1.6x (`rms_norm_backward`) and 2.1x
  (`layer_norm_backward`), and the 16M-element optimizers get **slower**, 0.80x - 0.88x: one thread already
  moves 29 GB/s, which is the machine's limit, and 12 threads only add overhead. Cache-resident cases scale
  5-6x on 12 threads (6 physical cores): `layer_norm` 1024x768 6.0x, `rms_norm` 5.0x, `layer_norm_backward`
  4.8x, `adam` at 1M elements 5.7x. For the large optimizers an automatic one-thread fallback above a size
  threshold would be a measurable win but is not implemented.
- `layer_norm` backward is slower than PyTorch for small and mid shapes (0.19x at 32x768, 0.64x at
  1024x768 on one thread), at parity for 8192x1024 and 1.1-1.9x faster on the largest. I did not find
  the cause of the small-shape gap: the likely contributors are the two extra passes that recompute mean
  and variance (PyTorch uses saved statistics) and baseline SSE2, but two attempted fixes did not help
  (see Tuning history). RMS norm backward has the same structure and is faster than PyTorch's autograd
  path, so a missing piece is specific to layer norm.
- `batch_norm` for `[N, C]` input: the forward is 1.3x - 2.8x faster than PyTorch after the fix, but its
  backward is 0.30x - 0.69x. NCHW is at parity or better (forward 0.85x - 2.0x, backward 1.05x - 1.5x).

## Native C++ PyTorch comparison

The reference executable calls our direct CPU kernels and preallocated C++ ATen `out` operators.
Both sides use identical F32 input/output addresses, default parameters, the shared timer and
checksum, and the same requested thread count. ATen operator dispatch is included; MensurFlow's
public Tensor API, allocation, view packing, backward and Python are excluded. This measures those
call boundaries rather than end-to-end model or Tensor-API performance.

### Build and conditions

- GCC 13.3.0, portable Release/OpenMP build; CUDA, Metal, OpenBLAS and `MENSURFLOW_NATIVE` OFF.
- CPU PyTorch `2.15.0+cpu`, whose configuration reports AVX2, MKL and OpenMP. NumPy is unnecessary
  for this executable. The imported Torch target requires C++20 for the reference executable;
  MensurFlow and the harness retain C++17. All three use GNU C++11 ABI 1.
- Full optional-reference build completed; **20/20 CTest executables passed in 10.59 seconds**.
  A native six-variant smoke run passed both libraries' independent float64 checks.
- CMake warned about the wheel's missing optional `kineto` profiler and a potential system/wheel
  `libgomp` runtime-path conflict. Runtime inspection found one loaded OpenMP library, the wheel's
  `torch/lib/libgomp.so.1`; both full runs also record their loaded path in JSON metadata.
- The user confirmed the machine was on AC with heavy programs closed. AC online and the
  `performance` CPU governor were read before and after each run. Background load and temperature
  were not independently sampled.
- Sizes: 1,000, 32,769 and 1,000,000; requested intra-op threads: 1, 2, 6 and 12; ATen inter-op: 1.
  Environment: `OMP_NUM_THREADS=12 OMP_DYNAMIC=FALSE OMP_PLACES=cores OMP_PROC_BIND=spread`.
  Each row sets and checks both thread-count getters. The printed initial ATen count of 6 is a
  startup snapshot, not the setting used for every row. Actual worker use follows each kernel's
  policy; MensurFlow's 1,000-element calls remain serial for every requested count.
- Each library is checked against float64 immediately before its timings. One warmup and nine
  calibrated samples (at least 2 ms each) per row, plus a 500 ms settling pause before each library.
  Run 1 times MensurFlow first; run 2 reverses this order, following another three-minute cooldown.

### Results and stability

Both full runs exited successfully with **144 timing rows each (288 total)** and empty stderr.
All pre-timing float64 checks passed for both implementations at every selected thread count.
Run 1 followed a 185.47 s cooldown and lasted 78.51 s; run 2 followed
a 186.86 s cooldown and lasted 78.03 s. Both loaded only the wheel's `libgomp.so.1`.

### Interpretation limits and optimization evidence

Inputs cycle through 13 values in `[-0.75, 0.75]`, including six negative values, six positive values
and zero. Timings do not cover extreme tails or softplus's linear shortcut; those have separate
correctness tests. Repeated calls reuse the same buffers. At one million elements the input and
output occupy 8 MB, within this CPU's 16 MB L3; reported GB/s counts logical reads/writes and is not
a measured DRAM bandwidth ceiling.

GCC's `-fopt-info-vec-all` diagnostic for the portable `-O3 -fopenmp` build reports that none of the
six new activation loop instantiations vectorized, including leaky ReLU. It cites control flow,
and scalar math calls (`expm1f`, `erfc`, `exp` and `log1p`) for the applicable operations. This
establishes a concrete SIMD optimization target. It does not isolate the percentage of runtime due
to branching, math calls, double intermediates or library dispatch. The existing cutoff of 32,768
was not tuned by this comparison.

## Historical leaky ReLU AVX2 follow-up (subsequently removed)

Measured code: `24f5445` plus uncommitted leaky ReLU SIMD changes. The preceding six-activation
tables describe the portable implementation before this follow-up; the other activations retain
that implementation. The forward Tensor API, dispatcher and CPU adapter are unchanged. The added
activation backward rules were later removed as noted above.

### Implementation and verification

- Runtime AVX2 CPU/OS check, eight F32 lanes, ordered negative comparison, protected inactive-lane
  multiplication, original-bit pass-through, unaligned memory access and a scalar tail.
- The portable shared loop remains available on unsupported hardware and as an internal benchmark
  baseline. A baseline OpenMP wrapper distributes 2,048-element chunks; the parallel cutoff remains
  32,768. Serial SIMD calls bypass the serialized OpenMP region. This measures the complete changed
  implementation path, not an isolated SIMD instruction gain.
- GCC 13.3 portable Release/OpenMP build: **20/20 tests passed, 14.04 seconds**. A separate fresh
  OpenMP-OFF build passed activation, packed-GEMM and packer checks: **3/3, 8.79 seconds**.
- Exact-bit tests cover all lengths 0–33 plus large odd sizes, aligned/unaligned pointers, guard
  regions, exact in-place use, thread counts, signed zeros, subnormals, infinities, negative slopes
  and quiet NaN payloads. Computed NaNs are checked by kind; pass-through NaNs retain their bits.
- Disassembly of the Release range helper contains `vmovups`, `vcmplt_oqps`, `vandps`, `vblendvps`,
  `vmulps` and YMM `vpcmpgtd` instructions. Its baseline wrapper and OpenMP worker contain no AVX
  instructions. Compile commands for SIMD, portable and GEMM sources have no global `-march`,
  `-mavx*` or `-mfma` flags.
- Leaky ReLU needs AVX2 alone. The initial shared feature-detection refactor and non-x86 GEMM cache
  fix were subsequently reverted; current detection is local to the elementwise implementation,
  and GEMM matches `24f5445`. ARM and Windows execution were not available; successful Linux/GCC
  checks do not verify those platforms.

### Focused measurement method

Same CPU, portable Release build, CPU Torch package and power/governor checks as above. Focused
sizes are 1,000/32,769/1,000,000 with 1/2 requested threads and slope 0.01. Environment:
`OMP_NUM_THREADS=2 OMP_DYNAMIC=FALSE OMP_PLACES=cores OMP_PROC_BIND=spread`.

Two measurement scopes remain separate:

1. `cpu_parallel_benchmark leaky_relu` and `leaky_relu_scalar` compare the selected implementation
   with the preserved portable path. Both use the same CPU harness, four-array allocation and
   system OpenMP runtime. Each section's `vs seq` still measures threading; the cross-implementation
   ratio below is portable median / selected median at a matching size/thread count.
2. `activation_torch_benchmark leaky_relu` compares selected MensurFlow and ATen within that native
   process, with identical input/output addresses, three-array allocation, wheel OpenMP runtime and
   500 ms settling before each library. Its scope remains a direct kernel vs an ATen `out` operator.

These harnesses have different allocations, output-address usage, runtimes and settling policies.
Do not combine absolute times between them or attribute their differences to a particular cause
without additional measurement. All previous input-distribution, cache and logical-bandwidth limits
still apply. No per-operation cutoff was tuned.

```bash
OMP_NUM_THREADS=2 OMP_DYNAMIC=FALSE OMP_PLACES=cores OMP_PROC_BIND=spread \
  ./build-cpu/cpu_parallel_benchmark leaky_relu --sizes=1000,32769,1000000
OMP_NUM_THREADS=2 OMP_DYNAMIC=FALSE OMP_PLACES=cores OMP_PROC_BIND=spread \
  ./build-cpu/cpu_parallel_benchmark leaky_relu_scalar --sizes=1000,32769,1000000
OMP_NUM_THREADS=2 OMP_DYNAMIC=FALSE OMP_PLACES=cores OMP_PROC_BIND=spread \
  ./build-torch-bench/activation_torch_benchmark leaky_relu \
  --sizes=1000,32769,1000000 --threads=1,2
```

## Bool comparisons and where

Measured code: `24f5445` plus uncommitted scope corrections and the planned comparison/selection
operations. The manual leaky ReLU AVX2 implementation has been removed; all new kernels use ordinary
C++ loops with the existing OpenMP macro and 32,768-element cutoff. Existing GEMM files match
`24f5445`, and the unary backward callback matches the pre-activation `f5f580a` implementation.

### Implementation and verification

- Six F32 comparisons return canonical Bool bytes, using one shared comparison template. IEEE
  comparisons make only `ne` true for a NaN operand; positive and negative zero compare equal.
- Bool/F32 `where` uses nonzero mask bytes to select the corresponding value, with no arithmetic
  masking. It retains selected quiet NaN payloads and signed zeros. The public APIs broadcast,
  pack views, allocate fresh outputs and validate kernel support even for empty results.
- Existing `(op, execution device, first-input dtype)` dispatch remains unchanged. `where` supplies
  value inputs before its Bool condition internally, so both comparisons and selection register
  CPU F32 keys. No new autograd, dtype conversion, GPU or GEMM kernels are included.
- GCC 13.3 portable Release/OpenMP build: **21/21 tests passed, 10.78 seconds**. OpenMP-OFF activation
  and selection checks: **2/2, 0.35 seconds**. Tests include independent logical broadcasting,
  metadata/views/offsets/empty/errors, IEEE truth tables, Bool storage, bit selection, thread
  invariance, exact in-place low-level `where`, and the public `gt → where` pipeline.
- Normal and native benchmark smoke checks passed all seven operations (7/14 timing rows) with
  empty stderr. Both modes rejected eight malformed/oversized CLI cases before allocation.
- A separate `-O3 -DNDEBUG -fopenmp -fopt-info-vec-all` compilation reports automatic 16-byte-vector
  processing for all six comparison loop instantiations at `elementwise.cpp:33`. `where` at line 67
  remains scalar because of control flow. This is compiler diagnostic evidence, not a measured
  scalar/SIMD speedup. No global `-march`, `-mavx*` or fast-math flags were introduced.

### Measurement method

`selection_benchmark` uses the shared nine-sample harness, one warmup, calibrated samples of at
least 2 ms, and a 500 ms pause before each timed library. It calls our direct CPU kernels and
preallocated native C++ ATen `out` operations with identical input/output addresses. ATen dispatch
is included; MensurFlow public API validation/packing, allocation, wrapping, checksums and Python
are outside the timer. Every implementation passes an independent scalar correctness check before
timing, with output sentinels preventing stale data from being accepted.

Same CPU/compiler/CPU Torch `2.15.0+cpu` as the earlier native session. Both builds use portable
Release/OpenMP settings; the optional native executable takes Torch's C++20 requirement while the
core retains C++17. The reference is optional and OFF by default. Normal mode remains independent
of Torch. Reference mode uses the wheel's OpenMP runtime, whose loaded path is captured per run.

Sizes are 1,000, 32,769 and **4,000,003**; requested intra-op threads are 1, 2, 6 and 12, inter-op is
1. Both intra-op getters are checked for every pair. Environment:
`OMP_NUM_THREADS=12 OMP_DYNAMIC=FALSE OMP_PLACES=cores OMP_PROC_BIND=spread`. Worker usage for small
inputs follows each implementation's own policy. The user had previously confirmed AC/quiet
conditions; AC online and the governor are read before/after. Background load and temperature are
not independently sampled.

`fill_a`/`fill_b` provide deterministic finite values. The where mask repeats true,true,false,false,
false. This checks a specific distribution rather than all possible masks or floating-point inputs;
special values have separate unit tests. Repeated calls reuse buffers, but the large case's active
comparison footprint (two F32 reads plus Bool output) is 36,000,027 bytes, above this CPU's 16 MiB
L3. For `where`, the logical upper bound is 52,000,039 bytes including both value branches. Smaller
cases can remain cached.

GB/s counts **9 logical bytes/element** for comparisons and an upper bound of **13** for `where`.
The scalar `where` may load only the selected branch; caches, write allocation and actual physical
traffic are not measured. Copy-bandwidth ceiling and percentage of ceiling remain `n/a`, pending

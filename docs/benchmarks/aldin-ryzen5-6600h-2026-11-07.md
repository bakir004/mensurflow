## Native C++ PyTorch comparison

The reference executable calls our direct CPU kernels and preallocated C++ ATen `out` operators.
Both sides use identical F32 input/output addresses, default parameters, the shared timer and
checksum, and the same requested thread count. ATen operator dispatch is included; MensurFlow's
public Tensor API, allocation, view packing, backward and Python are excluded. This measures those
call boundaries rather than end-to-end model or Tensor-API performance.

### Build and conditions

- GCC 13.3.0, portable Release/OpenMP build; CUDA, Metal, OpenBLAS and `MENSURFLOW_NATIVE` OFF.
- CPU PyTorch `2.15.0+cpu`, whose configuration reports AVX2, MKL and OpenMP. NumPy is unnecessary
  for this executable. The imported Torch target requires C++20 for the reference executable;
  MensurFlow and the harness retain C++17. All three use GNU C++11 ABI 1.
- Full optional-reference build completed; **20/20 CTest executables passed in 10.59 seconds**.
  A native six-variant smoke run passed both libraries' independent float64 checks.
- CMake warned about the wheel's missing optional `kineto` profiler and a potential system/wheel
  `libgomp` runtime-path conflict. Runtime inspection found one loaded OpenMP library, the wheel's
  `torch/lib/libgomp.so.1`; both full runs also record their loaded path in JSON metadata.
- The user confirmed the machine was on AC with heavy programs closed. AC online and the
  `performance` CPU governor were read before and after each run. Background load and temperature
  were not independently sampled.
- Sizes: 1,000, 32,769 and 1,000,000; requested intra-op threads: 1, 2, 6 and 12; ATen inter-op: 1.
  Environment: `OMP_NUM_THREADS=12 OMP_DYNAMIC=FALSE OMP_PLACES=cores OMP_PROC_BIND=spread`.
  Each row sets and checks both thread-count getters. The printed initial ATen count of 6 is a
  startup snapshot, not the setting used for every row. Actual worker use follows each kernel's
  policy; MensurFlow's 1,000-element calls remain serial for every requested count.
- Each library is checked against float64 immediately before its timings. One warmup and nine
  calibrated samples (at least 2 ms each) per row, plus a 500 ms settling pause before each library.
  Run 1 times MensurFlow first; run 2 reverses this order, following another three-minute cooldown.

### Results and stability

Both full runs exited successfully with **144 timing rows each (288 total)** and empty stderr.
All pre-timing float64 checks passed for both implementations at every selected thread count.
Run 1 followed a 185.47 s cooldown and lasted 78.51 s; run 2 followed
a 186.86 s cooldown and lasted 78.03 s. Both loaded only the wheel's `libgomp.so.1`.

**39 of 72 paired combinations exceeded 10% timing drift.** These measurements are a baseline,
not sufficiently stable evidence for tuning cutoffs or claiming small performance wins. In
particular, softplus at 32,769 elements/12 requested threads changed its ATen median from 5.9719 to
0.06213 ms: the apparent 34.40x MensurFlow advantage in run 1 reversed in run 2. Exact GELU and
softplus also had large million-element/12-thread outliers. Cooling and reversing call order did not
eliminate this variability; these logs do not establish its cause.

For a compact comparison, all six million-element/**2-thread** combinations stayed within 10%
between runs. Every activation was slower than ATen at this size/thread count. Values below are
run 1 / run 2, in milliseconds; `torch/ours < 1` favors ATen.

### Interpretation limits and optimization evidence

Inputs cycle through 13 values in `[-0.75, 0.75]`, including six negative values, six positive values
and zero. Timings do not cover extreme tails or softplus's linear shortcut; those have separate
correctness tests. Repeated calls reuse the same buffers. At one million elements the input and
output occupy 8 MB, within this CPU's 16 MB L3; reported GB/s counts logical reads/writes and is not
a measured DRAM bandwidth ceiling.

GCC's `-fopt-info-vec-all` diagnostic for the portable `-O3 -fopenmp` build reports that none of the
six new activation loop instantiations vectorized, including leaky ReLU. It cites control flow,
and scalar math calls (`expm1f`, `erfc`, `exp` and `log1p`) for the applicable operations. This
establishes a concrete SIMD optimization target. It does not isolate the percentage of runtime due
to branching, math calls, double intermediates or library dispatch. The existing cutoff of 32,768
was not tuned by this comparison.

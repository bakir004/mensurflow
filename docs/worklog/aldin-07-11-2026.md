## Summary

Completed the CPU F32 activation implementations: `leaky_relu`, GELU (Gaussian CDF and tanh forms),
SiLU, ELU and softplus. All five use one shared templated loop and the existing Tensor/dispatcher
architecture. Added parameter forwarding, CPU registrations, autograd rules, independent references,
tests and benchmark coverage.

## What changed

1. Completed leaky ReLU end to end, including configurable slope and its saved backward parameter.
2. Added the remaining four activations with stable tails/overflow handling, documented infinity and
   zero-gradient conventions, and validation of softplus parameters.
3. Added `activation_test` for low-level kernels, the public API and finite-difference gradients;
   extended the dispatcher coverage test.
4. Added the six activation benchmark variants (including GELU approximation), independent checks
   before timing, and an optional `--sizes=...` argument for focused runs.
5. Added the optional native C++ `activation_torch_benchmark` target and a standard-library-only
   paired-log parser, `benchmarks/reference/compare_native_activations.py`. Both libraries write to
   the same preallocated buffers. The earlier Python timing prototype was removed after the native
   comparison became available, to avoid maintaining two competing measurement paths.
6. Updated the README/kernel coverage and added `docs/ACTIVATIONS.md` with API and benchmark commands.

## Architecture review follow-up

The API -> dispatcher -> CPU adapter -> shared loop structure was reviewed again. Added explicit
backward checks at signed zero, infinities and NaN; corrected a duplicate stale GELU checklist entry.
The new benchmark size option now rejects counts that would overflow its padded four-array
allocation. Malformed, nonpositive and maximum-int64 sizes were checked to fail before allocation.

Two pre-existing autograd issues were reproduced independently of the new activations: a reused
intermediate propagates only its first contribution to parents, and a transposed view stores a
gradient in the view's shape on its base tensor. Their examples and scope are documented in
`docs/ACTIVATIONS.md`. They need core autograd fixes before relying on these graph patterns.

After these review changes, all **20/20 tests passed again** in 11.41 seconds. A fresh short benchmark
of all six variants at sizes 1,000 and 32,769 with 1/2 threads completed successfully. Invalid-size
checks covered maximum int64, zero, negative, trailing-comma and nonnumeric inputs.

## Native reference follow-up

After the user installed CPU PyTorch `2.15.0+cpu`, the separate optional LibTorch build passed
**20/20 tests in 10.59 seconds**. A six-variant native smoke run and malformed CLI checks passed.
The NumPy warning from importing Torch does not affect the C++ executable.

The user confirmed AC power and a quiet machine; AC online and the `performance` governor were
checked before/after. Two full runs used sizes 1,000/32,769/1,000,000 and 1/2/6/12 requested threads,
with measured cooldowns of 185.47 and 186.86 seconds. Run 2 reversed library timing order. Both exited
successfully, produced 144 timing rows and empty stderr, and passed all pre-timing float64 checks.

The paired parser flagged **39/72 combinations above 10% timing drift**, including severe outliers
at 12 threads. These results cannot establish tuned defaults or stable small wins. At one million
elements and two threads, all six pairs were within 10% drift and all were slower than ATen. The
[same-day report](../benchmarks/aldin-ryzen5-6600h-2026-11-07.md#native-c-pytorch-comparison)
retains every paired result and its limitations.

A separate GCC vectorization diagnostic confirmed that none of the six new activation loop
instantiations vectorized in the portable build, including leaky ReLU. Control flow and scalar math
calls provide concrete optimization targets. No SIMD implementation or cutoff was changed here.

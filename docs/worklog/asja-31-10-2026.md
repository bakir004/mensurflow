## 1. Understanding the code

Found that `Shape`, `Strides` and `Tensor` were on `origin/main`, not on my old branch, and read them:

- `Shape` and `Strides` are plain `int64` vectors. The element at index `(i, j, ...)` is at
  `offset + sum(index * stride)`. Strides count elements, not bytes.
- `Tensor` is shared storage plus offset, shape, strides and dtype. Views (`transpose`, `slice`,
  `expand`, `unsqueeze`, `view`) only change the metadata, no data is copied.
- `copy_to_host` follows strides with an odometer walk for non-contiguous views.
- `Device` is a type plus an index, with a parser for strings like `cuda:1`.

## 3. What I built

**Dispatcher and backends** (`src/core`, `src/backends`)

- `Buffer`, `Stream`, `Backend` interface, a registry, and a dispatcher keyed by (op, device, dtype).
  A missing kernel throws `NotImplemented`; an explicit device never silently falls back.

  `contiguous()`, `item<T>()`.
- GPU backends are optional at build time (`MENSURFLOW_CUDA`, `MENSURFLOW_ROCM`, `MENSURFLOW_METAL`).

**Public ops:** `dot`, `add`, `sub`, `mul`, `div` (with broadcasting), `matmul`.

**CPU kernels**

- One helper, `src/backends/cpu/parallel.hpp` (`parallel_for`, `parallel_sum`); kernels have no pragmas.
- A plain sequential version of every kernel in `sequential.cpp`, used as the benchmark baseline.
- `matmul`: cache-blocked, rows of C split between threads.

**GPU backends**

- CUDA (cuBLAS), ROCm (rocBLAS), Metal (MPSGraph). No `div` on CUDA or ROCm (no BLAS call for it).
- Built and tested CUDA on the RTX 3060 (CUDA 13.4, MSVC): 11 of 11 tests passed, no source changes.

**Tests:** 13 test programs, including float64 references and checks that the sequential and
parallel versions agree.

## 4. Results

Laptop (i7-10510U, 4 cores, on battery, so noisy; the same row varies by 30-40 % between runs):

| Op | Parallel vs sequential |
|---|---|
| `dot` | 3.5-5.4x at 10M+ elements |
| `matmul` | 3.5-4.3x from n = 128 (44 GFLOP/s peak, 58 with AVX2/FMA) |
| `add`, `mul` | at most about 1.4x (limited by memory bandwidth) |
| `add`, `mul` at 100k | slower than sequential (about 0.3x with 8 threads) |

CUDA on the RTX 3060: `dot` reaches 329 GB/s (about 91 % of peak) and beats the CPU above ~100k
elements. Elementwise ops only reach 23-50 GB/s (cuBLAS workaround plus a per-call allocation).

Desktop (Ryzen 9 5900X) results were added from an earlier benchmark and are marked as needing a
rerun with the current one.

## 5. Problems found and fixed

- **Laptop state:** on battery, Balanced power plan, mismatched RAM (3200 and 2667 MHz sticks).
  Recorded in the benchmark doc.
- **Benchmark bug:** sequential `mul` was about 2x slower than `add` because the arrays were laid out
  at the same offset within a page (4K aliasing). Fixed by staggering the arrays 1 KB apart.
- **Test bug:** my broadcasting reference mishandled a size-0 dimension and crashed the test. The
  library was correct.
- **Setup:** the pre-commit hook needs `clang-format` (used the one in the LLVM install through
  `PRS_CLANG_FORMAT`); VS Code was not reading the project's settings because the folder was not
  opened as a project, and the C/C++ extension cannot read response files in `compile_commands.json`;
  Windows Application Control blocked a few freshly built test executables (rebuilt, not bypassed).

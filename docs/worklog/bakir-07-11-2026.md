## 1. What I built

**`gemm_strided_batched`** (`include/mensurflow/ops/blas.hpp`, `src/ops/blas.cpp`,
`src/backends/cpu/ops/gemm/gemm_batched.{hpp,cpp}`)

- `alpha * op(a[i]) * op(b[i]) + beta * c[i]` over a batch, with NumPy-style broadcasting of the batch
  dimensions (`[B, M, K] x [K, N]`, `[2, 1, M, K] x [5, K, N]`), both transpose flags, and a `c` that
  broadcasts to the result.
- Nothing is copied: transposes are swapped strides, broadcast batch dimensions are `expand()` views with
  stride 0, and the CPU adapter turns the batch index into one offset per matrix. Built on Asja's packed
  strided GEMM, so her faster kernel speeds it up too.
- Two ways to use threads: `over_batch` (threads split the batch, one matrix per thread) and
  `within_matrix` (each matrix split over all threads). The default picks one from the shapes.
- Not differentiable yet, and no GPU kernel.

**`concat`, `split`, `pad`** (`include/mensurflow/ops/movement.hpp`, `src/ops/movement.cpp`,
`src/backends/cpu/ops/movement/movement.{hpp,cpp}`)

- `concat` along any axis: the output is cut into pieces of at most 16,384 floats inside one input row,
  so even a concat along axis 0 (one long row per input) is spread over the threads; each piece is a
  `memcpy`.
- `split` by chunk size or by a list of sizes: returns views, like `torch.split`, so it has no kernel.
- `pad` in constant mode with PyTorch's padding order (pairs from the last dimension). One output row per
  iteration: either all fill, or fill, a `memcpy` of the input row, fill. Negative padding (cropping)
  and the reflect and replicate modes are not supported yet.

**`ger`** (stretch): `alpha * outer(x, y) + a`, rows split across threads.

## 3. Benchmarks and results (M3 Pro, one session)

Full tables and the conditions are in the
[result file](../benchmarks/bakir-m3pro-2026-11-07.md).

**Reference comparison** (reference time / ours, above 1 means we are faster):

| op | size | ours / reference |
|---|---|---|
| batched GEMM | 1024 x 8³ | 2.90 vs `torch.bmm` |
| batched GEMM | 64 x 128 x 128 x 64 | 0.30 vs `torch.bmm`, 0.74 vs NumPy |
| batched GEMM | 4 x 512³ | 0.09 vs `torch.bmm` |
| concat | 16M floats | 1.21 vs `torch.cat` |
| concat, 8 inputs | 16384 x 1024 | 2.69 vs `torch.cat` |
| pad | 4096 x 4096 | 3.63 vs `F.pad` (PyTorch also allocates) |
| ger | 4096 x 4096 | 1.06 vs `torch.addr` |

- The data-movement ops reach 124 to 150 GB/s out of cache, close to the M3 Pro's advertised 150 GB/s
  (not a measured ceiling: the all-threads copy benchmark does not exist yet).
- Batching pays off for small matrices: 20x faster than calling `matmul()` per matrix for 1024
  matrices of 8 x 8, 4.7x for 64 of 128 x 128, about the same for 4 of 512 x 512.

**Problems found and fixed**

- `concat` and `pad` were 6 to 9 times slower on 11 threads than on one just above the elementwise
  cutoff (32,768 elements). They now use the 262,144-element cutoff; those sizes stay on one thread.
- My first PyTorch run was single-threaded because the script set `MKL_NUM_THREADS=1`, which PyTorch
  also reads. Fixed in the script; the numbers are from the second run.

## Not done / open

- **Batched GEMM is 3 to 11 times behind `torch.bmm` for matrices of 128 and up on this Mac.** Two
  reasons: (1) on ARM the packed GEMM is not vectorized and falls back to plain loops for every matrix (a
  NEON micro-kernel would fix it with no change to the batched code); (2) PyTorch and NumPy use Apple
  Accelerate, which runs on the AMX matrix unit, not the CPU cores. A fair comparison needs OpenBLAS on
  this Mac or a run on the team's x86 machines, where the AVX2 packed kernel is used. Not done yet.
- No measured ceilings: `fma_peak_benchmark` does not build on ARM (it includes `immintrin.h`
  unconditionally; not my file, so I left it), and there is no all-threads bandwidth benchmark yet.
- Not differentiable yet: `gemm_strided_batched`, `concat`, `pad`, `ger`.
- `pad`: only constant mode, no negative padding.
- The weekly plan's definition of done still says "parallel_for / parallel_sum (no pragmas in kernels)";

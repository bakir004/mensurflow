## Summary

Profiled `matmul` and last week's six functions with AMD uProf 6.0 on the Ryzen 9 5900X, added the
driver used for it (`benchmarks/profile_driver.cpp`), and vectorized the worst kernel the profile
found, `max_pool2d` forward, with AVX2: 3.5x to 8.6x on one thread, up to 6x at 24 threads on
small batches; at batch 32 it now runs at the memory bandwidth (as `avg_pool2d` already did).

## Profiling setup

* `build-prof/` (gitignored): Release flags plus `/Zi` and `/DEBUG /OPT:REF /OPT:ICF`, so uProf
  finds the function names (`build-opt/` has no PDBs). The commands are in the header of
  `benchmarks/profile_driver.cpp`.
* `profile_driver <op> [seconds] [threads]` runs one parallel kernel in a loop, so the profile holds
  nothing else (the benchmarks also run the sequential baselines and other shapes).
* `AMDuProfCLI collect --config assess_ext` (cycles, instructions, branches and mispredictions, L1
  refills by source, misaligned loads, store-to-load conflicts), 8 s per op, 24 threads. Without
  administrator rights only user-mode samples are collected, which covers the kernels.
* `memset`/`memcpy` appear as `vcruntime140.dll!0x...` (no symbols). Demand refills from DRAM read
  close to zero for streaming kernels because the hardware prefetchers fetch the lines; compare GB/s
  with `bandwidth_benchmark` (36.1 GB/s copy, read + write) instead.

## max_pool2d forward with AVX2

`src/backends/cpu/ops/conv/pooling.cpp`. The parallel kernel computes 8 output columns of a row at
once. Each lane keeps its own best value and index and scans its window in the sequential order; a
cell replaces the best if it is strictly greater (an ordered compare, false for NaN) or if it is a NaN
while the best is not. That is the scalar rule lane by lane, so values (to the bit, including -0/+0)
and indices are identical to `max_pool2d_f32_sequential`.

* Stride 1: one load per cell; stride 2: `p[0..7]` and `p[7..14]`, the even elements picked with a
  shuffle and a 64-bit permute (nothing past the last cell is read); other strides: a gather.
* Columns whose window touches the padding (column 0 of the ResNet stem pool) and the columns after
  the last full block stay on the scalar loop; the last block may overlap the one before it.
* Selected at run time (`packed_gemm_supported()`, as the optimizers do), and only for planes
  below 2^31 cells (32-bit lane indices).
* Test `test_vector_paths` in `tests/ops/max_pool2d_test.cpp`: strides 1-4, kernel widths 1, 2, 3,
  5, every allowed padding, widths 8-57, values with NaN, infinities, signed zeros and ties; bitwise
  values and indices against the sequential kernel at 1 thread and all threads. Changing the compare
  to `>=` makes it fail.

Results (`profile_driver maxpool_fwd`, uniform random input, ms per call; old and new alternated):

| threads | before | after |
|---|---|---|
| 1 | 174 | 17.2 |
| 12 | 15.7 | 5.48 (32.8 GB/s) |
| 24 | 9.9 | 5.74 |

`pooling_benchmark --batches=1,32 --threads=1,12,24` (median ms, before -> after): r18 3x3/2 N=1
1 thread 1.706 -> 0.485, 24 threads 0.285 -> 0.046; N=32 1 thread 54.8 -> 16.8, 12 threads 5.54 ->
5.33 (memory-bound both times); 2x2/2 128ch N=1 1 thread 0.489 -> 0.179, 12 threads 0.079 -> 0.018;
small 3x3/1 8ch 0.0179 -> 0.0060. Global 7x7 (one output column) keeps the scalar loop. The gain on
one thread depends on the data: the benchmark's input is smoother than uniform random values, so
the old loop mispredicted less there (3.3x instead of 8.6x).

After the change, uProf at 12 threads: `max_pool_block8<2>` 56%, scalar edges 26% (before the stride-2
load was made exact; the last column now runs vectorized too), workers 14%.

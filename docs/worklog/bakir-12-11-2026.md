## 1. What I built

**Softmax** (`include/mensurflow/ops/softmax.hpp`, `src/ops/softmax.cpp`,
`src/backends/cpu/ops/softmax/softmax.{hpp,cpp}`)

- `softmax`, `log_softmax`, `softmax_backward`, `log_softmax_backward` along any axis. The kernel sees
  the input as [outer, length, inner] and gives each line to one thread, so the bits are the same at
  every thread count.
- Stable: the line maximum is subtracted before `exp` and the sum is kept in double; log-softmax is
  `(x - max) - log(sum)`. A line that is all -inf gives zeros (log: -inf) instead of NaN, so fully
  masked attention rows are defined. A NaN poisons its line.
- Autograd: the backward ops use the forward output, saved without its autograd state so the node does
  not keep itself alive.

**Losses** (`include/mensurflow/ops/loss.hpp`, `src/ops/loss.cpp`, `src/backends/cpu/ops/loss/loss.{hpp,cpp}`)

- `Reduction { None, Sum, Mean }` on every loss, as `docs/KERNELS.md` asks. Mean of nothing is NaN (as in
  PyTorch), sum is 0.
- `cross_entropy(logits [N, C], labels [N] int64)`: fused per row (logsumexp minus the label's logit),
  no softmax stored. The one-hot needed by the gradient is built inside the backward kernel (one
  subtraction per row), so it does not depend on `one_hot`. Labels are checked on the host first.
- `mse_loss` and `binary_cross_entropy_with_logits`, which uses `max(x, 0) - x t + log1p(exp(-|x|))`.
  Autograd covers both the input and the target.
- Reduced losses sum fixed 16,384-element chunks in parallel and then add the chunk sums in order:
  the loss is bit-identical on 1 and 11 threads.

**Attention** (`include/mensurflow/ops/attention.hpp`, `src/ops/attention.cpp`)

- `attention(q, k, v, mask, causal, scale)`: `gemm_strided_batched(q, k^T, scale)`, `where(mask, s, -inf)`,
  `softmax`, `gemm_strided_batched(p, v)`. It uses the existing batched GEMM and `where` without
  changing them, as the plan asked. Bool masks broadcast to the scores; `causal` is top-left aligned like
  PyTorch's `is_causal`. Forward only: the batched GEMM has no backward yet.

**Wiring**: 10 new `OpId`s, a `reduction` field in `OpArgs`, CPU registration, public headers in
`mensurflow.hpp`, and the 11 ops added to the observability runner, so each has a page in the dashboard.

## 2. Tests (`tests/ops/softmax_loss_test.cpp`, `tests/reference/softmax_loss.hpp`)

- Kernels against double-precision references at 1, 2, 3 and all threads, on shapes below, at and above
  the cutoff, with long lines (20,000 and 32,000) and strided lines (inner > 1), and checks that the bits
  do not change with the thread count.
- Edge cases: logits of +-1000 and 1e4, fully masked lines, NaN lines, BCE at x = +-100 and 30.
- API: axes including negative and 0-d, transposed views, empty inputs, every reduction, and 15 error
  cases (labels out of range, wrong dtypes and shapes, wrong upstream gradient shapes).
- Autograd: softmax, log-softmax over axis 0, MSE and BCE for input and target, and cross-entropy
  against finite differences. Changing the labels after forward does not change the gradient.
- Attention against a scalar reference: plain, mask, causal, both with an explicit scale, a query with
  no visible key (zeros), k and v broadcast over heads, and errors.

## 3. Benchmarks and results (M3 Pro, one session, our side run twice)

Full table and conditions: [result file](../benchmarks/bakir-m3pro-2026-11-12.md). Ceiling: copy at
123 GB/s on 11 threads (`bandwidth_benchmark`).

**Reference comparison** (PyTorch time / ours, best thread counts, above 1 means we are faster):

| op | ours / PyTorch |
|---|---|
| softmax | 1.23 to 1.63, except 16384 x 512 (0.84) |
| log_softmax | 0.57 to 0.78 (1.38 at 64 x 1000) |
| softmax / log_softmax backward | 0.50 to 0.84 |
| cross_entropy | 0.62 to 0.89; backward 0.94 to 0.99 (2.5 at 64 x 1000) |
| mse_loss, bce_with_logits and backward | 1.05 to 16 |
| attention | 0.73 to 0.84 of PyTorch's naive version, 0.09 to 0.20 of its fused SDPA |

**Problems found and fixed**

- `mse_loss_backward` was 1.6 to 4 times slower with threads at 65,536 elements; it now uses the 262,144
  cutoff (memory-bound, like concat and pad last week).
- `log_softmax` lost about 3e-5 near logits of 1000 (rounding `max + log(sum)` to float); now exact.
- The cross-entropy and BCE backward kernels crashed on an empty batch with `Reduction::None` (they read
  `gradient[0]`).
- BCE's gradient `sigmoid(x) - t` lost three digits at x = 8, t = 1; rewritten without the cancellation.

## Not done / open

- **Softmax, log-softmax and cross-entropy are 0.5 to 0.65x of PyTorch on one thread at large shapes**
  because `std::exp` is a scalar libm call per element (clang cannot vectorize it) while ATen uses a
  vectorized polynomial `exp`. All threads only reach 4 to 17% of the memory ceiling. Next: a
  vectorizable `exp` in plain C++ (range reduction plus a polynomial), shared by softmax, cross-entropy and
  BCE. It is the same fix the scalar `sigmoid`, `tanh` and `gelu` need.
- `softmax_backward` reads its inputs twice and reaches 74% of the memory ceiling (PyTorch 97%).
- `attention` is forward only and materializes the full score matrix; it needs `gemm_strided_batched`
  backward for training, and FlashAttention-style tiling (P4) to approach the fused SDPA.
- No `ignore_index`, class weights or label smoothing in `cross_entropy` yet (label smoothing is a P1
  backlog item).
- Only measured on the M3 Pro; the x86 machines have not run it.

## Dependencies

- Aldin's `cross_entropy` needs his own `log_softmax`; its gradient needs `one_hot` (Bakir). Until it lands,
  build the one-hot inside the loss kernel. Label smoothing builds on `cross_entropy`.
- Bakir's attention needs Aldin's `softmax`; until then, do the RNG, `dropout`, `one_hot` and `embedding`.
- Bakir's `dropout` needs his RNG. `hardmax` uses his `one_hot` and the existing `argmax`.
- Bakir's `unique` can use Asja's `sort` when it lands; until then sort inside the kernel.
- Asja's `einsum` uses the existing `permute` and Bakir's `gemm_strided_batched` without changing them.
- Aldin's accuracy is composed from `argmax`, `eq` and `mean`; no new kernel.
- `logsumexp` (Aldin) and `log_softmax` (Aldin) share the same stable max-and-sum pass.

## Same definition of done as last week

Sequential version, parallel version, dispatcher registration, public op, tests against a reference in
`tests/reference/`, a benchmark row, and a comparison with the best available implementation (PyTorch,
OpenBLAS and so on). See [last week's plan](2026-11-04-plan.md#same-definition-of-done-for-every-function);
the measuring rules there still apply. Views (`squeeze`, `select`, `as_strided` and so on) need no kernel and
no benchmark, only tests. Tick the box in `docs/KERNELS.md` in the same commit as the function.

Sequential and parallel: most existing kernels are one loop whose `MENSURFLOW_PARALLEL_FOR(if n > cutoff)`
runs on one thread below the cutoff; only `matmul`, `max`, `min` and the batched GEMM have separate
`_sequential` and `_parallel` functions. Bakir decides whether new functions need the separate pair.

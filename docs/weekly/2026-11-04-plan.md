### How to measure so the comparison is fair

These are the traps we already fell into on matmul. Each one changed a number by 20% or more.

- **Same conditions for both sides:** same machine, same session, same dtype (float32), same shapes and
  memory layout, same thread count (`torch.set_num_threads(n)`, `openblas_set_num_threads(n)`, our
  `set_max_threads(n)`), output written into preallocated memory on both sides where the library allows
  it (`out=` in PyTorch). Check that the results agree before you time anything.
- **Pause before every timed library (about 500 ms).** OpenBLAS's and OpenMP's worker threads keep
  spinning after a call and take cores from whatever runs next. Without the pause our kernel read 376
  instead of 620 GFLOP/s.
- **Report the median and the minimum of at least 9 runs**, and repeat the whole comparison. At high thread
  counts OpenBLAS's median varied by 40% between runs; a single run proves nothing.
- **Thread counts:** 1, a few in between, the number of physical cores, and all hardware threads. On a CPU
  with SMT, compute-bound code gains nothing from the second thread of a core, so do not read the
  all-threads row as "the CPU is slower".
- **Compare at the sizes users have:** small (about 1,000 elements, where call overhead dominates), around
  the parallel cutoff, and large (far beyond the caches). A kernel that wins at one size and loses at
  another is a result, not a failure.
- **Release build, no `MENSURFLOW_NATIVE`, plugged in, quiet machine**, as in
  [`docs/benchmarks/README.md`](../benchmarks/README.md).
- **Record the versions:** PyTorch (and the output of `torch.__config__.show()` and
  `torch.__config__.parallel_info()`), OpenBLAS (our benchmark prints it), the compiler, the CPU.

### Say how close you are to the hardware, not only to the reference

A library can itself be far from what the CPU can do. For each function give a ceiling:

- **Compute-bound** (`gemm`, batched `gemm`): the measured FMA peak, from `fma_peak_benchmark` (112 GFLOP/s
  per core and about 1320 GFLOP/s for the whole chip on the Ryzen 9 5900X). Run it on your own machine
  first; peak numbers from the CPU's data sheet were 25% too high there.
- **Memory-bound** (elementwise, activations and their backward ops, copy, transpose, `concat`, `pad`,
  `cast`, `gather`): the measured copy bandwidth in GB/s, and the bytes your op must move (count every
  array read and written once).

### What to report and where

Add a "Reference comparison" table to your result file in `docs/benchmarks/` (and put the headline in your
worklog), one row per function, size and thread count:

| op | n or shape | threads | ours (ms and rate) | reference and version | reference (ms and rate) | ours / reference | percent of ceiling |
|---|---|---|---|---|---|---|---|

"Ours / reference" is the reference's time divided by ours, so 1.00 is parity and above 1.00 means we are
faster. A proposal for what to do with the number:

- Within 10% of the reference, or faster: done, say so.
- Slower by more than 25% at a size that matters: write one paragraph on why (not vectorized, memory
  bound, call overhead, threading) and what you would try next, in the worklog's "Not done / open".
- If the reference is far from the ceiling and we are too, that is a finding worth one line as well.

If PyTorch cannot be installed on your machine (about 200 MB; for the CPU wheel use
`pip install torch --index-url https://download.pytorch.org/whl/cpu`), say so in your result file and use
OpenBLAS, Eigen or NumPy for that function. Keep the PyTorch scripts in `benchmarks/reference/`, one per
op group, printing the same columns as our benchmark tables, so a teammate can run them on another machine.

## From the professor's notes

These apply to everyone:

- **All kernels should be vectorized.** Write loops the compiler can vectorize (contiguous, no aliasing) and
  check it in the benchmark against the `scalar` baseline. Do not assume it; our default build only uses
  baseline SSE2, and `sqrt`, `exp`, `sigmoid`, `axpy` and `dot` were not vectorized by the compiler.
- **The main fallback is the parallel CPU implementation.** `Execution::Auto` already goes to the CPU.
- **Autotuning (later, not blocking anyone; written up as a proposal in `docs/plan/ARCHITECTURE.md`, section 5b):** the user can pick CPU or GPU explicitly, or let an autotuned
  call decide from the dimensions. The autotuner needs: a switch to turn it on, a log of the timed runs
  (the log is the autotune record), and several kernels with different block sizes to choose from.
  Bakir's item 3 is only the skeleton: the flag, the timing log, and the hook into `Execution::Auto`.

## Open questions

- When does the autotuner run? Proposal: with the flag on, on the first call for each combination of
  (op, dtype, device, size bucket); it times the candidates, logs the result, and reuses the winner.
- Does the log double as a persistent cache, so later runs skip tuning?
- Should `autotune(dot, a, b)` return the choice, run the op, or both?
- Does everyone have Python and PyTorch? If not, one person could run the PyTorch side for the others from a
  shared list of shapes and thread counts (a CSV in `benchmarks/reference/`), and the others compare against
  that file.
- Which PyTorch version do we pin for the comparisons, so that results from different machines can be put
  side by side?
- If a GPU kernel is missing (CUDA has no `div`), should `Execution::Auto` fall back to the CPU? The
  dispatcher now throws `NotImplemented`. Falling back for `Auto` only, and keeping the error for an explicit
  `Execution::GPU`, would be a small change.
